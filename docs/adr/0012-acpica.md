# ADR-0012: ACPICA 20260930, its core vendored unchanged, with an OS layer in Odin, for `bus-acpi`

Status: proposed, import review pending (`third_party/VENDOR.ndb`, `reviewed.by=pending`), 2026-10-04.

## Context

Upstream's M5 step 7 runs ACPICA in user space, in `bus-acpi` (its 01 §7.2, ADR-0024 and ADR-0030): it loads the firmware's DSDT and SSDTs, runs their AML, lists the devices present and their resources for `devmgr`, and powers the machine off through S5. Four M5-era scenarios this tree is judged by need it (`tests/qemu/m5/acpi.ndb`, `acpiarm.ndb`, `rtc.ndb`, `poweroff.ndb`). Writing an AML interpreter is out of the question; ACPICA is the one every OS but Windows uses. ACPICA calls an OS services layer (`AcpiOs*`, `acpiosxf.h`) that its host provides. Upstream writes that layer in C inside `bus-acpi`; this tree has no first-party C (ADR-0002, ADR-0003), and ADR-0007 already set the pattern for vendored C behind a thin layer of Odin with C-ABI exports.

## Decision

- **ACPICA 20260930** (2026-09-30), the release upstream vendors, from `github.com/open-acpica/acpica`, is vendored unchanged under `third_party/acpica`, with only its OS-independent core kept (`subset=`): `source/include` and nine directories of `source/components` (dispatcher, events, executer, hardware, namespace, parser, resources, tables, utilities), about 86 kLOC. iASL, the disassembler, the debugger, the tools and the tests are left out. Licence: BSD-3-Clause or GPL-2.0-only; taken under BSD-3-Clause.
- **Provenance.** ACPICA's releases are not signed and publish no checksum. The tarball was fetched over HTTPS on 2026-10-04 and hashes to `sha256=` in `VENDOR.ndb`, the same hash upstream recorded from its own fetch the day before; the subset unpacked from it matches `tree.sha256=`, and is byte-identical to upstream's vendored copy (it is Intel's and the ACPICA project's code, not upstream VectraOS's, so ADR-0002's clean-room rule does not apply to it). When reviewing, compare the kept files with the release's git tag.
- **No generated files.** ACPICA's core needs none; `ports/acpica` holds only `port.ndb` and the port's environment header.
- **The build** is `tools/build`'s, from `ports/acpica/port.ndb`: a native port (`native=yes archive=yes`), compiled once per architecture and cached (`out/acpica/<arch>`) by the general mechanism for vendored C in Odin programs (`tools/build/cobj.odin`, ADR-0011), freestanding and not PIC, with upstream's stack protector for native programs restored in `cflags=` (`-fstack-protector-strong -mstack-protector-guard=global`) and the port's own flags (`-std=gnu11 -O2`, frame pointers kept, `-w`), into `libacpica.a`, which `bus-acpi` links (`cports = {"acpica"}`). Upstream's `-fcf-protection=full` and `-mbranch-protection=standard` are not passed: cobj.odin has no per-architecture flags, and the Odin objects beside ACPICA carry neither, so the linked program would not have them anyway. The tree has no platform header for VectraOS, and its `acenv.h` stops at an unknown one, so `ports/acpica/acvectra.h`, force-included, takes `acenv.h`'s place: 64-bit, the system's C library, ACPICA's own object caches, no debugger, and a global lock that is always free (there is no FACS). `./build vendor-check` covers the tree.
- **The OS layer is Odin** (`servers/bus-acpi`, package `bus_acpi`): each `AcpiOs*` procedure ACPICA calls is a `proc "c"` exported under ACPICA's name, as are the few C library functions ACPICA calls once it is told the C library is the system's (`memcmp`, `strlen`, `strcmp`, `strncmp`, `strcpy`, `strncpy`, `strcat`, `strchr` and eight `ctype` functions; Odin's runtime gives `memset`, `memcpy` and `memmove`), and the stack protector's `__stack_chk_guard` and `__stack_chk_fail`. `AcpiOsPrintf`, variadic, is written with Odin's `#c_vararg` and `intrinsics.c_va_start`, and passes its `va_list` to ACPICA's own `vsnprintf` (`utprint.c`), as `AcpiOsVprintf` does. Port I/O at 16 and 32 bits is a small `.S` file of `bus-acpi`'s own (`servers/bus-acpi/arch/x86_64/io.S`).
- **ACPICA's types in Odin.** What the OS layer and `bus-acpi` read or write of ACPICA's (`ACPI_OBJECT`, `ACPI_BUFFER`, `ACPI_DEVICE_INFO`, `ACPI_PNP_DEVICE_ID`, `ACPI_PCI_ID`, `ACPI_PREDEFINED_NAMES`, the packed `ACPI_RESOURCE` and the resource kinds it uses, the scalar types, the status codes and constants), and the ACPICA procedures it calls, are declared in Odin in `servers/bus-acpi/acpica`, with `#assert` on each size and offset. A host test, `tests/host/acpica_layout`, compiles one `_Static_assert` per size, offset and constant, with Odin's values, against ACPICA's headers under `acvectra.h` for both targets, as `tests/host/musl_layout` does for musl. (It found a wrong `AE_BAD_DATA` on its first run.)
- **What the layer does** is upstream's behaviour: the tables come from the kernel's copies (the `acpi` VMO), laid out in an address range of the layer's own behind a synthesized RSDP and XSDT, since the firmware's memory they came from may since have been reclaimed; memory, I/O ports and PCI configuration space are asked of `devmgr` when the AML first touches them (M5 step 7b, upstream's ADR-0024 item 4) and kept; one thread, so locks and semaphores are counters and deferred work runs at once; memory from a heap of power-of-two free lists over one 8 MiB VMO. Whether the hardware is reduced (no sleep registers: power off is PSCI, through `devmgr`) is read from the FADT's copy, the bit ACPICA's `AcpiGbl_ReducedHardware` is set from, rather than from ACPICA's global: Odin has no usable `foreign` variables (ADR-0003).

## Known limits

- The FACS is not among the kernel's copies, so ACPICA runs without it: no global lock shared with the firmware, no waking vector. QEMU's AML takes no global lock; a real machine's may.
- One thread: what ACPICA would defer runs at once, and a semaphore wait that would block times out at once.
- The SCI is not delivered: events are set up but never handled.

## Consequences

- Upgrading is replacing the tree with the next release's subset, checking whether a new file in the nine directories needs a line in `port.ndb`'s `sources=`, rebuilding, and running `tests/host/acpica_layout`, which catches a changed layout.
- ACPICA's code is not under the house rules; it builds with its own flags and warnings, and is not linted, as for musl and Lua.
- `bus-acpi` links its archive through cobj.odin, as Monocypher's users do; cobj.odin also hashes a port's own directory (`acvectra.h`) into its cache key. A program's own assembly (`DIR/arch/ARCH/*.S`) is assembled beside lib/rt's (`tools/build/progasm.odin`).
