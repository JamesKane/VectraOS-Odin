# ADR-0006: u9fs, vendored as a host test tool

Status: proposed, 2026-10-04. Review of the import pending (`reviewed.by=pending` in `third_party/VENDOR.ndb`).

## Context

M3 asks that the 9P stack be tested against one stock 9P2000 server, so that `vx:p9` is not tested only against itself (upstream's docs/04 §5). Upstream chose `u9fs`, the Plan 9 project's own 9P2000 server for Unix, over 9front's `exportfs` (Plan 9 only) and `diod` (9P2000.L only) (upstream ADR-0006). Its `u9fs` scenario is one of the M3-era scenarios this tree is judged by (`tests/qemu/m3/u9fs.ndb`).

## Decision

- `u9fs` is vendored unchanged under `third_party/u9fs`: the Plan 9 Foundation's tree at commit `ed1a9c2` (2025-10-28), `sys/src/cmd/unix/u9fs`. Upstream has no release tarball, so `VENDOR.ndb` pins the directory's git tree id (`git.tree=7ce2c33…`), which the files reproduce. The tree was copied from upstream VectraOS's vendored copy at `ec7b1ef` and is byte-identical to it (same tree id, same tree hash `426ecd59…15a52`); it is the Plan 9 Foundation's code, not upstream VectraOS's, so ADR-0002's clean-room rule does not apply to it, as it does not to Limine (ADR-0005).
- It is a **host test tool only**: `build` compiles it into `out/host/u9fs` for the `u9fs` scenario, with the pinned clang, rebuilding when any file of the tree is newer than the binary. It is never part of an image.
- It builds as upstream left it except for two constants its `rune.c` uses and nothing defines (`Bit5` and `Runemax`, from an unfinished change to 21-bit runes). `build` supplies Plan 9's values on the command line (`-DBit5=2 -DRunemax=0x10FFFF`), so the tree stays byte-identical. It compiles as GNU C89 with warnings off: it is old code, not ours, and not under the house rules.
- `u9fs` serves `/` and confines itself only with `chroot`. The scenario runner therefore runs it, through QEMU's `guestfwd` at 10.0.2.101!564, in an unprivileged user namespace (`unshare -r`), chrooted into a fresh copy of the test fixtures that also holds the one-line `etc/passwd` and `etc/group` its user lookups read, with `-a none -u vectra -n`.
- Where unprivileged user namespaces are missing (macOS, or a Linux that turns them off), the runner reports the `u9fs` scenario skipped and why, and leaves the forward out of QEMU's command line.

## Consequences

- `vx:p9`'s client meets a server written by others. Upstream's first finding stands for this tree too: Plan 9 servers refuse an attach as `none` until a connection has authenticated, so dialed connections attach as `vectra`.
- Interoperability is tested in QEMU only, through `guestfwd`; a host without unprivileged user namespaces (the macOS development host among them) cannot run that scenario, so it runs on the Linux host only.
- On every upgrade: fetch the new tree, check its git tree id, update `VENDOR.ndb`, and see whether the two command-line constants are still needed.
