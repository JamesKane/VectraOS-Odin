# Upstream findings

Bugs the port found in upstream VectraOS, behaviour this tree deliberately does differently, and why. Each is worth reporting upstream.

| Found | Where upstream | What | Here |
|---|---|---|---|
| P2 clean-up | `kernel/obj/device.c` (M2) | `iorange_create` accepts a 65,536-port range (`end > 0x1'0000`) and stores its count in a `uint16_t`: 0, so the task gets no ports while the console is still handed off. | Fixed in this tree before upstream's M3 fixed it the same way (`count` as 32 bits). |
| P3 | `lib/vx-ns` (M3) | Unmount lets a connection go once no *mount* uses it, even while a *bind* still holds a fid on it; the next walk through that bind follows a null client and crashes. | Any member, mount or bind, keeps the connection. Found by comparing random namespace scripts against upstream's C. |
| P3 | `kernel/arch/*/arch.c` (M3) | Not a bug: M3 makes FP/SIMD trap in user tasks until the kernel saves it. | ADR-0004: saved eagerly at every entry, so user tasks have it; ktest checks that it works where upstream checks that it faults. |
| P3 | `servers/netd/netd.c` (M3) | A query's answer is held in 256 bytes and cut there, silently: `/net/dns` for a name of more than 236 bytes (names may have 253) answers with a line cut short, its address truncated and no newline, and with four addresses, names of more than 44 bytes overflow it. | Kept as upstream does it, byte for byte (the answer is built whole, then its first 256 bytes kept); a fix would size the answer for `DNS_ADDRS` lines of the longest name. |
| P4 | `lib/vx-rc/rc.c` (M4) | A pipeline stage with a file redirection: the redirection's path is freed as the redirection is undone, but the stage runs afterwards, so the host reads the path from freed heap memory. Found by cross-checking a million mutated scripts against upstream's C. | The path is freed with the deferred close, after the stage has run. |
| P4 | `lib/vx-debug/eval.c` (M4) | A pointer difference divides by a type size the target supplies; a hostile size of 2^64−1 traps (SIGFPE) in the debugger. | The division wraps. |
| P4 | `lib/vx-debug` unwinder (M4) | x86_64: past `push %rbp` the frame record is assumed at sp, wrong after callee-saved pushes before `prologue_end`. aarch64: an outer frame's sp is taken as fp+16, so SP-relative locals are read from the wrong place. | Kept, for byte-for-byte output; a host test documents the aarch64 case. |
| P4 | `kernel/arch/*/arch.c`, `kernel/obj/exception.c` (M4 step 2c) | Not a bug: M4 keeps each thread's FP/SIMD registers in its thread object, saved with FXSAVE (or q0-q31) at each switch, and a stopped thread saves them for a debugger (`user_held`). | ADR-0004's design stays: the state is saved at every entry, in the trap frame (XSAVE, AVX included, on x86_64), so a stopped or suspended thread's registers are always there. `.Get_Fpregs`/`.Set_Fpregs` read and write that area in place: on x86_64 the XSAVE area's legacy region, which is FXSAVE's image, with a component XSAVE left in its initial state (XSTATE_BV clear) written out as such, and a set marking x87 and SSE present; the YMM upper halves are not in a `vx_fpregs` and are left as they were. MXCSR, FPCR and FPSR are made safe as upstream makes them. Only the thread pointer is saved at each switch, as upstream does. |
| P4 | `lib/vx-rt/note.c` (M4 step 4e) | Not a bug: the in-task note entry saves FP/SIMD state with FXSAVE, which upstream's x86_64 user state is (it never enables AVX). | Here user code may use AVX (ADR-0004), so the x86_64 entry saves with XSAVE, every component XCR0 enables, in 4 KiB of the thread's stack. |
| P4 | `lib/vx-note/note.c` (M4) | Not a bug: `vx_trap_note`, Plan 9's words for a trap, is a header both the kernel and vx-rt include. | It is `vx.trap_note` in `abi/vx/note.odin`, which the kernel and `vx:rt` both import, as the text is part of the interface (a parent reads it as the exit string). Checked against upstream's C on the host: 864 cases (every kind, code 0-3, six addresses, three pcs), byte for byte. |
| P4 | `lib/vx-rt/rt.c` (M4 step 4e) | Not a bug: `vx_main` returns its exit string. | `vx_main` still returns an int here, until the programs are ported to M4: 0 ends the program with the empty string, anything else with its decimal value, as APE's `exit(n)` does. `rt.exits(msg)` ends it with a string. |
| P4 | `kernel/boot.c` (M4 step 3e) | Not a bug: the kernel asks Limine for five entropy values, the first for its stack protector's guard. | It asks for four, all for the root task's `entropy=` record: Odin's code has no stack protector. |
| P4 | `kernel/sched/sched.c` (M4 step 4c) | Not a bug: `vx.hangdump=N`, a debugging aid that prints every thread N seconds after boot. | Not ported. |
| P4 | procfs's debug path with a musl program (M4) | Not a bug upstream, which only debugs vx-rt programs: a musl program's signal handler, declining a fatal fault, runs the instruction again (its `vx_note_crash`), and the kernel offers the debugger that fault a second time, so the crash never reaches procfs's crash directory while a debugger is attached. Here `dbgdemo` runs on musl (ADR-0007). | procfs passes on, without a second stop, a fault identical to the one it just passed on for that thread. |
| P5 | `lib/vx-fat` `fat_dir_next` (M5) | A long-name slot numbered 0 with a matching checksum writes 26 bytes before a stack buffer (ASan: stack-buffer-underflow); a hostile disk triggers it. | Such a slot forms no name. |
| P5 | `lib/vx-fat` (M5) | Twenty long-name slots of characters at U+0800 and above decode to 780 bytes, overrunning `fat_entry.name[766]` into `alias`. | The name buffer holds 780 bytes. |
| P5 | `lib/vx-fat` `fat_write` (M5) | The `offset + count > UINT32_MAX` check wraps near 2^64; the gap loop then zero-fills the volume. | Overflow-checked. |
| P5 | `lib/vx-iso` `iso_record_at` (M5) | The next offset and the padding skip are 32-bit: a directory extent near 4 GiB wraps them and `iso_dir_next` loops forever, so a hostile image hangs isofs. | 64-bit offsets. |
| P5 | `lib/vx-iso` `iso_sector` (M5) | A failed read leaves the evicted cache slot valid under its old sector; a partial read caches corrupt data as that sector. | A slot whose read failed is marked invalid. |
| P5 | `lib/vx-driver` `blkclient.c` (M5) | A driver reporting a sector larger than the 1 MiB arena gives `max == 0`, and reads and writes loop forever on zero-length requests: a broken driver hangs fsd. | Refused with `Err_Unsupported`. |
| P5 | `lib/vx-iso` (M5) | `iso_each_su` and `iso_decode` keep function statics, so they are not reentrant (harmless in isofs today). | No statics. |
| P5 | `build.c` (M5 steps 6c, 6d) | Not a bug: from M5 upstream's runner gives every scenario the machine's IOMMU (q35's intel-iommu, virt's `iommu=smmuv3`) and its virtio devices `iommu_platform=on`. | The m5/ scenarios get it (and `iommu=caching`, VT-d's caching mode, as upstream); M4's scenarios (`tests/qemu/m4/`) run without one, as M4's runner ran them, so the M4 gate is judged as it was. |
| P5 | `tests/kernel/ktest.c` (M5 step 6d) | Not a bug: the check that a DMA mapping's device addresses are contiguous from 4 GiB is unconditional, since upstream's runner always has an IOMMU. | ktest makes it where the firmware describes an IOMMU (a DMAR table, or an IORT with an SMMUv3 node: virt always has an IORT, for its ITS), so m4/ktest still passes; m5/ktest makes it on both architectures. ktest also checks `system_power`'s refusals and `clock_set`, which upstream's does not. |
| P5 | `kernel/obj/exception.c` (M5 step 5a) | Noted: a pager's late page is `VX_EXCEPTION_PAGER_TIMEOUT` ("page not supplied") only to a debugger, an in-task handler or an exception port. A task no one handles it for is killed by the architecture's default with the original page fault's words ("sys: trap: fault read addr=…", the unaligned address), since the kind changes only inside `exception_raise`. | Kept, for the same exit strings. |
